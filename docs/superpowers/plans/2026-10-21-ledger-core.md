# Ledger Core Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** An immutable double-entry ledger in `ledger/` that proves money is never created, lost or paid twice.

**Architecture:** Thin ActiveRecord models describe the data; every write goes through service objects in `app/services/ledger/`. Postgres enforces the invariants that matter (check constraints, a composite currency foreign key, a deferred balancing trigger, immutability triggers). Posting locks `account_balances` rows `FOR UPDATE` in ascending account id order and checks available balance before writing.

**Tech Stack:** Ruby 4.0.7, Rails 8.1.4 (API mode), PostgreSQL 18.6, RSpec + FactoryBot (latest stable), RuboCop (rubocop-rails-omakase), GitHub Actions.

**Spec:** `docs/superpowers/specs/2026-10-21-ledger-core-design.md`

## Global Constraints

- Latest stable releases of every gem; add new gems with `bundle add <gem>` (no pre-releases), pinned by `Gemfile.lock`.
- Amounts are integers in minor units (`amount_minor`, cents). `$100.00` is `10000`. No Float or BigDecimal anywhere in the domain.
- No ledger gems (double_entry, keepr). No gems beyond rspec-rails and factory_bot_rails unless a task names one.
- Every invariant that matters is enforced in Postgres, not only in Ruby. Schema is kept as `db/structure.sql`.
- Writes go only through `Ledger::*` service objects; models and tests (other than DB-guard tests) never insert entries directly.
- No HTTP API, controllers or routes in this feature.
- All accounts, people and amounts are invented. Never name any real employer or company anywhere in code, docs or commits.
- Work only inside the repo. Commit after each task; do not push.
- All commands run from `ledger/` unless stated.

## Review Focus

1. **Two entries on the same account in one transaction** (e.g. debit and credit `employer_cash` with other legs). Expect the account locked once, deltas summed, balance row correct. Test: Task 3, `same account twice`.
2. **Amounts that are not Integers** (`"10000"`, `100.0`, `BigDecimal("100")`, `nil`) or unknown `direction`. Expect `Ledger::InvalidRequest`, nothing written. Test: Task 3, `non-integer amounts`.
3. **Unknown account code.** Expect `Ledger::NotFound`, nothing written, key not consumed. Test: Task 3 and Task 4 (`failed post leaves no key`).
4. **Retry seconds later with `effective_at` omitted, or with metadata keys / entries in a different order.** Expect a replay, not a conflict. Test: Task 4, `replay tolerates ordering and omitted effective_at`.
5. **Holds on a credit-normal account.** Expect capture to decrease the held account on its normal side (debit it) and the counter account to take the opposite side. Test: Task 8, `capture on a credit-normal account`.

**Interfaces:**
- Consumes: `Account`, `AccountBalance`, `Ledger::Balance.posted_minor`, errors.
- Produces:
  - Table `ledger_transactions`: `idempotency_key text not null unique`, `request_hash char(64) not null`, `effective_at timestamptz not null`, `metadata jsonb not null default '{}'`, `reverses_id bigint unique references ledger_transactions`, `created_at timestamptz not null default now()` (no `updated_at`).

**Interfaces:**
- Consumes: `PostTransaction.call(..., operation: "capture", release_held: { account_id => amount })`.
- Produces:
  - Table `holds`: `account_id not null references accounts`, `amount_minor bigint not null check (> 0)`, `status text not null default 'active' check in (active, captured, released)`, `idempotency_key text not null unique`, `request_hash char(64) not null`, `ledger_transaction_id bigint unique references ledger_transactions`, timestamps, `check ((status = 'captured') = (ledger_transaction_id is not null))`.
  - `Ledger::PlaceHold.call(key:, account_code:, amount_minor:) -> Hold`. Locks the balance row, checks `available >= amount` unless `allow_negative`, inserts the hold, `held_minor += amount`, `version += 1`. Idempotent like posting (hash of `operation: "place_hold"`, account code, amount).
  - `Ledger::CaptureHold.call(hold_id:, key:, counter_account_code:, amount_minor:) -> Hold`. `1 <= amount_minor <= hold.amount_minor` else `InvalidRequest`. In one transaction: lock the hold row, then `PostTransaction` with two legs that decrease the held account on its normal side and give the counter account the opposite side, `metadata: { "hold_id" => id }`, `release_held: { hold.account_id => hold.amount_minor }`; set `captured` + `ledger_transaction_id`. Replay with the same key on a captured hold returns it; a different payload under that key raises `ConflictError`.
  - `Ledger::ReleaseHold.call(hold_id:) -> Hold`. Lock hold, then balance row; `held_minor -= amount`; `released`. Releasing a released hold returns it unchanged.
  - Any other transition raises `Ledger::InvalidState`. Unknown hold raises `Ledger::NotFound`.
  - `expect_ledger_consistent!` also asserts each balance's `held_minor` equals `Hold.where(status: "active", account_id:).sum(:amount_minor)`.

**Interfaces:**

- Produces: `Ledger::ReverseTransaction.call(transaction_id:, key:) -> LedgerTransaction`.
